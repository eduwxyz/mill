## Problem Statement
The visualizer can inspect only one Mill database per server process. People working across multiple projects must restart or reconfigure it to change context, and project identity is absent from both API requests and browser links. This makes it difficult to compare or monitor projects from one visualizer URL and creates a risk that an unscoped archive action targets the wrong database when session identifiers overlap.

## Solution
The visualizer will serve multiple configured local projects from one process and one URL. Each project has a URL-safe name that identifies it in API paths and hash routes, and the UI lets people choose that project before viewing, tailing, prompting, or archiving its sessions. A project configuration can name an explicit database or a repository whose standard Mill database location is inferred. Existing single-database invocation remains supported: it is represented internally as one project and retains the existing unprefixed API compatibility routes. In multi-project mode, all UI traffic is explicitly project-scoped and unprefixed routes are unavailable, preventing accidental writes to the default project.

## User Stories
1. As a visualizer user, I want to configure several local Mill projects for one visualizer process, so that I can inspect them without restarting or changing the server command.
2. As a visualizer user, I want each configured project to have a stable, URL-safe name, so that I can tell which project's data a link and request address.
3. As a visualizer user, I want to configure a project with either a database location or a repository location, so that common project setups need less repeated path information.
4. As a visualizer user, I want home-directory shorthand and config-relative paths to resolve predictably, so that a portable project configuration does not depend on the directory from which I start the visualizer.
5. As a visualizer user, I want a selected default project, or the first configured project when no default is set, so that opening the visualizer has a deterministic destination.
6. As a visualizer user, I want the legacy database command-line and environment configuration to keep its current precedence when no project configuration is supplied, so that my existing single-project workflow continues to work.
7. As a visualizer user, I want the browser URL to include the project before the session and phase, so that copied links preserve the context needed to show the intended data.
8. As a visualizer user, I want a bare visualizer hash route to take me to the default project, so that the root entry point is useful without requiring a manually constructed project link.
9. As a visualizer user, I want a project picker when more than one project is configured, so that I can move between projects from the same visualizer instance.
10. As a visualizer user, I want a single configured project to look like the existing visualizer, so that added multi-project capability does not add unnecessary controls to the common workflow.
11. As a visualizer user, I want the selected project visible in navigation and breadcrumbs, so that I can verify context before acting on a session.
12. As a visualizer user, I want session lists, session details, live events, phases, envelopes, gates, prompts, and archive actions to be scoped to the selected project, so that no view or action mixes data from another database.
13. As a visualizer user, I want switching projects to discard the previous project's view state, timers, and card state, so that late responses or reused session identifiers do not display as the newly selected project's data.
14. As a visualizer user, I want cards from different projects with the same session identifier to remain distinct, so that normal identifier collisions cannot reuse stale UI state.
15. As a visualizer user, I want the project list to show whether a configured database is currently available without opening every database, so that opening the picker remains cheap and one unavailable project does not disrupt healthy projects.
16. As a visualizer user, I want a configured project without a database yet to be reported as temporarily unavailable rather than unknown, so that I know to run an ADW and can try again without restarting the visualizer.
17. As a visualizer user, I want the visualizer to retry an unavailable project when I request it, so that a database created after startup becomes usable in the same server session.
18. As a visualizer user, I want an unknown project name to receive a distinct not-found response, so that malformed or stale project links are distinguishable from a project that has not produced data.
19. As a visualizer user, I want the project list refreshed when I open the picker and after a temporary-unavailable response, so that a project that becomes live is discoverable without perpetual background polling.
20. As a visualizer user, I want my old unprefixed API workflow to remain byte-for-byte compatible while exactly one project is active, so that existing single-project automation and manual use are not disrupted.
21. As a visualizer user in multi-project mode, I want unprefixed API endpoints to fail rather than silently use a default project, so that an archive request cannot write to the wrong database.
22. As a visualizer operator, I want one malformed or missing configured database not to prevent the server from serving other projects, so that partial configuration failures have limited impact.
23. As a visualizer operator, I want database connections closed when the process is interrupted, so that the multi-project server shuts down cleanly.
24. As a visualizer user with an old session-only hash link, I want a clear unknown-project outcome and access to the picker, so that the deliberate removal of ambiguous legacy link parsing does not silently show unrelated data.

## Implementation Decisions
The visualizer gains a project-configuration resolver and a `ProjectRegistry`; the existing `MillDb` remains a one-database abstraction and is not changed. Project configuration exposes a required unique `name` and a resolved database location. A project entry accepts exactly one of a database location or a repository location; the latter maps to the standard Mill database location. Names must satisfy the existing safe URL-segment validation and serve as both URL identity and display label.

Project configuration is selected by `--projects <file>` or `MILL_PROJECTS_CONFIG=<file>`, with the command-line option taking precedence. Configuration paths expand `~`; relative locations resolve from the configuration file's directory. The optional `default` must select a configured project; if omitted, the first project is default. When neither selector is present, the existing single-database resolver, including its `--db`, `MILL_DB`, and working-directory precedence, supplies one legacy project.

`ProjectRegistry` owns entries containing project name, resolved database location, an optional open `MillDb`, and the latest open error. Its public contract provides `list()`, `get(name)`, and `close()`. `list()` returns project name, database location, availability, and error without opening a database; availability is based on database-file existence. `get()` lazily opens the requested database. It reports an unknown configured name separately from a configured database that cannot open, retains the latter error for reporting, and retries its open on every subsequent request. Shutdown closes every database opened by the registry.

The server factors the current session endpoint behavior into a reusable route group that accepts a request-to-database resolver. Scoped routes use `/api/projects/:project/` followed by the current endpoint shapes for health, sessions, session detail, events, envelopes, gates, agent prompts, and archive. A scoped unknown project returns 404; a known project whose database is unavailable returns 503 with its retained error. `GET /api/projects` always returns registry project information. When and only when there is exactly one project, the route group is also mounted at the existing unprefixed endpoints using that project's database; it is not mounted unprefixed for multiple projects. Route-group creation and registry creation remain usable without starting a listening server.

The client API contract takes `project` as its first argument for every project-bound fetch and mutation. A single URL builder percent-encodes the project segment and constructs all scoped API URLs; the client also fetches project information from the project-list endpoint. No UI call uses an unprefixed endpoint.

The hash-route contract is `#/<project>/`, `#/<project>/<adw_id>`, and `#/<project>/<adw_id>/<phase_id>`. Route state contains `project`, `adwId`, and `phaseId`, and link generation requires the project. The root hash redirects to the default project. Legacy session-only hash parsing is intentionally not supported because it is ambiguous with a project name.

The application loads projects at startup, chooses the configured default for a root route, and refreshes project information when the picker opens or a scoped request receives 503. The top bar renders a plain project name for one project and a selector for multiple projects; project is the first breadcrumb segment. Session list, session card, session trace, and phase detail receive and propagate project context for every read and mutation. Existing component remount behavior is extended with project-inclusive keys for session traces, session lists, and session cards, resetting polling and local state on a project change and preventing cross-project reuse where session IDs coincide.

## Testing Decisions
The primary test seam is the exported route group mounted with a `ProjectRegistry` and temporary Mill databases. It tests observable HTTP behavior at the highest seam that can prove database isolation, route mounting, status mapping, and archive safety without a browser or a listening production server. In particular, two databases sharing a session identifier must show that archiving through one project leaves the other unchanged; this directly protects the feature's silent-wrong-database risk.

Configuration resolution is tested as a pure resolver seam because option/environment precedence, legacy fallback, and path interpretation are contractual behavior independent of HTTP. Tests cover project-selector precedence and the no-selector branch preserving existing database resolution behavior.

Route mounting is tested through the same server seam: unprefixed endpoints work when exactly one project resolves and are absent or return not found when multiple projects resolve. This verifies the intentional safety boundary rather than handler internals.

The repository has no existing TypeScript test suite and its current general test command runs Python unit tests only. The visualizer adds Bun's test runner and these focused tests rather than introducing a lower-level mocking seam or a browser suite. Tests assert responses and persisted database outcomes, never registry fields, component keys, or handler implementation details.

## Out of Scope
This feature does not add remote database access, authentication, authorization, project discovery, live configuration reload, or changes to data written by the tracer. The project list is read at server startup; adding or removing configured projects still requires restart. It does not add a separate display-label field, preserve legacy session-only hash links, or permanently alias unprefixed APIs to the configured default in multi-project mode. It does not introduce periodic polling solely for project availability. These boundaries would change only with a separate decision about remote security, configuration lifecycle, stable external API compatibility, or a non-ambiguous legacy-link format.

## Further Notes
No ADR directory is present, so there are no recorded ADR conflicts to report. The configuration is JSON as decided by the provided shape; behavior for malformed configuration files, an empty project list, a `default` that names no project, and an entry specifying both or neither `db` and `repo` is not explicitly decided and should be defined before implementation. The user-facing 503 text for unavailable databases is described by the design, but the exact response error schema is not specified.
